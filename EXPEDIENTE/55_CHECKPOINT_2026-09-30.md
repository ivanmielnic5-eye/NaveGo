## Hallazgos tecnicos importantes

**H1: expo-sqlite y Headless JS**
No es incompatible. El problema era que foreground y Task
abrian 'navego.db' con la misma conexion cacheada. La solucion
es `useNewConnection: true` en la Task.

**H2: intervalo nominal del OS**
El OS entrega fixes cada ~2000ms, no 1000ms. El umbral de
deteccion de gap debe ser >2000ms. Se uso 3500ms.

**H3: android backup no funciona**
Android 12+ bloquea `adb backup` para apps sin debuggable.
La APK es release, no se puede leer la DB via adb. Para
verificacion de datos crudos hay que exportar desde la app.

## Fase 6 — Recuperacion de sesion ACTIVE

**Objetivo:** si el usuario aprieta INICIAR, cierra la app sin
finalizar (crash, swipe, bateria), y luego reabre, la sesion
se retoma automaticamente. El boton pasa a PAUSAR. La distancia
y el track estan precargados.

**Componentes:**

### db/journal.ts — funciones nuevas
- getActiveSession(db): devuelve sesion ACTIVE mas reciente,
  excluyendo TASK_TEST. Devuelve {id, title, total_distance,
  last_processed_seq} o null.
- getProcessedRoutePoints(db, sessionId): devuelve puntos con
  has_new_point=1 para reconstruir el track.

### useNaveGoTracker.ts — useEffect de recuperacion
Al montar, si TASK_PRODUCER_ENABLED y no REPLAY:
1. Abre DB si no esta abierta.
2. Busca sesion ACTIVE.
3. Si existe:
   - sessionIdRef.current = id.
   - totalDistanceRef.current = total_distance.
   - routePointsRef.current = puntos de processed_points.
   - lastProcessedCursorRef.current = last_processed_seq.
   - isRecordingRef.current = true.
   - setea isRecording/isTracking/isPaused en React.
   - console.log('[TRACKER] Sesion retomada: ' + id + ...).
4. Si no existe: flujo normal. Solo punto azul, boton INICIAR.

**Regla:** una sola sesion ACTIVE a la vez. Sin umbral de
tiempo. Retoma siempre que exista.

### startTracking — guard de reuso
Si bootstrap recupero sesion, startTracking NO crea otra.
Reusa la existente. Log: 'startTracking reusa sesion'.

### Comportamiento al cerrar
Al cerrar la app sin finalizar, la sesion queda ACTIVE en
SQLite. La Task sigue capturando en background (si el OS la
deja correr). Al reabrir, se retoma.

### Al finalizar
stopTracking marca CLOSED, cierra DB. La sesion deja de ser
ACTIVE. Proxima apertura: flujo normal.

## WatchPosition liviano — ubicacion al abrir la app

**Problema:** al abrir la app sin sesion activa, no habia punto
azul en el mapa. La Task no alimenta el HUD hasta que hay
sesion (polling solo corre cuando isRecording=true).

**Solucion:** un watchPosition liviano que corre en foreground
cuando:
- TASK_PRODUCER_ENABLED=true
- REPLAY_ENABLED=false
- isRecordingRef.current=false

**Que hace:**
- watchPosition con interval 2000ms.
- En cada callback:
  - if isRecordingRef.current: return (no hacer nada, lo maneja
    el polling).
  - setLivePosition({lat, lon}).
  - lastFixTimestampRef.current = timestamp.
  - lastFixAccuracyRef.current = accuracy.
  - updateNavigationStatus(timestamp, accuracy).
- Al desmontar: subscription.remove().

**Que NO hace:**
- NO crea sesion.
- NO escribe a SQLite.
- NO suma distancia.
- NO aparece en Historial.

**Resultado:** al abrir la app, punto azul visible + GNSS con
estado correcto (CONFIABLE / DEGRADADO / NO DISPONIBLE segun
accuracy).

**Cuando el usuario aprieta INICIAR:**
- isRecordingRef.current pasa a true.
- El proximo callback del liviano hace return temprano.
- El polling toma el control.

**Cuando el usuario FINALIZA:**
- isRecordingRef.current vuelve a false.
- El liviano sigue corriendo (no se apaga).

## Fixes criticos de la tarde

### 1. Umbral de gap: 2000 -> 15000
**Sintoma:** 33 gaps abiertos y cerrados en 98 fixes.
**Causa:** el OS entrega fixes cada ~2000ms con jitter. Con
GAP_THRESHOLD_MS=2000, cualquier jitter disparaba gap falso.
**Fix:** subir a 15000. Los gaps reales (30s+) se siguen
detectando.
**Commit:** 5251505.

### 2. Gap por receivedAt, no measuredAt
**Sintoma:** gaps abiertos inmediatamente al recibir un fix.
**Causa:** la Task recibe fixes con measuredAt retrasado ~5s
(batching del OS). Con measuredAt, elapsed siempre >5000ms.
**Fix:** usar receivedAtMs para la deteccion.
**Commit:** bccdd6a + 3fdc041.

### 3. Polling suma distancia
**Sintoma:** track se dibuja (28 puntos) pero distancia queda
en 0.00m.
**Causa:** el polling actualizaba routePoints pero no sumaba
distance_delta a totalDistance.
**Fix:** acumular y sumar.
**Commit:** 976e844.

### 4. Polling actualiza navstatus
**Sintoma:** GNSS siempre NO DISPONIBLE o DEGRADADO aunque
llegaran fixes.
**Causa:** el polling no llamaba a updateNavigationStatus.
**Fix:** llamar con timestamp + accuracy en cada ciclo.
**Commit:** b6473cb.

### 5. Accuracy real via JOIN
**Sintoma:** GNSS degradado aun con fixes de accuracy baja.
**Causa:** el polling usaba un ref desactualizado.
**Fix:** getProcessedPointsSince hace LEFT JOIN con gps_fixes
para traer accuracy real.
**Commit:** beaf92e.

### 6. COG por geometria
**Sintoma:** COG en 0 con ghost movement (SOG < 0.3 m/s).
**Causa:** processFix usaba input.heading del GPS. El GPS
reporta heading=0 cuando cree que el celu esta quieto.
**Fix:** si hay newPoint (movimiento geometrico >= MIN_DELTA),
calcular COG por geometria aunque speed sea bajo.
**Aplica a los dos caminos** (watchPosition y Task).
**Commit:** 6ba3237.

### 7. Bootstrap revertido
**Intento:** crear sesion automaticamente al abrir la app.
**Problema:** cuando el usuario apretaba INICIAR, el guard
`if (isRecordingRef.current) return` lo frenaba. El boton
nunca cambiaba a PAUSAR.
**Fix:** revertir bootstrap. La sesion se crea SOLO al apretar
INICIAR.
**Commit:** 07539a6.

### 8. Task sin JSONL
**Sintoma:** la Task no escribia a SQLite. TaskService invocaba
pero no terminaba (no habia `Finished task`).
**Causa:** el JSONL (background_test.jsonl) crecia con cada
corrida. La Task lo leia y reescribia completo cada 2s.
Bloqueaba la ejecucion.
**Fix:** quitar el JSONL. Era evidencia de Fase 2, ya no
necesario. La DB (gps_fixes + processed_points) es evidencia
mejor.
**Commit:** 2cd2571.
