## Conceptos nuevos detectados (para LOGOS v1.2)

Registrados por critica de GPT-4. NO se implementan todavia.
Solo se anotan para no perder el hilo.

### RUNTIME DRIFT
El MANIFEST declara autoridad. El sistema puede tener piezas corriendo
que el MANIFEST no conoce. Eso fue exactamente lo del 22 sep.
Propuesta: comparar DECLARADO vs OBSERVADO (systemctl, ss, archivos,
procesos). Cuando no coinciden -> alerta.

### SYSTEM_INVENTORY
Capa intermedia entre MANIFEST (autoridad) y capsula (estado).
Declara que EXISTE: que piezas hay, donde viven, para que sirven.
Hibrido: la maquina descubre, el humano declara significado.
Cuando no coinciden -> alerta.

### HUMAN GATE
Acciones que SIEMPRE requieren autorizacion humana:
borrado irreversible, modificacion de secretos, cambio de permisos,
exposicion de puertos, cambios de firewall criticos, instalacion de
mecanismos persistentes, publicacion externa, decisiones de
arquitectura.
Regla: la IA no se adelanta cuando la accion es materialmente
irreversible.

### KPI real (correccion)
La latencia (0.24 ms) NO es el KPI principal.
Medir: objetivo alcanzado, tiempo hasta solucion, error de ruta,
freshness, uso CPU/RAM, tasa de errores.
Una latencia excelente en un algoritmo que no resuelve el objetivo
es una metrica enganosa.

### Hallazgo: puerto 8080 compartido (deuda tecnica)
El puerto 8080 sirve para DOS propositos distintos:
- En el celu: servidor HTTP embebido (nitro-http-server) que sirve
  tiles del mapa a MapLibre.
- En la mini PC: el bridge del daemon servia telemetria.
No compiten fisicamente (maquinas distintas). Pero es confusion
conceptual. Se anota como deuda tecnica.

## Conceptos nuevos detectados (segunda ronda, post-experimento DSH)

Registrados tras el experimento CORREDOR-SF-CABA. NO se implementan

### EVIDENCE como cuarta capa de LOGOS

Hasta hoy teniamos tres capas:
    MANIFEST  -> que tiene autoridad
    INVENTORY -> que existe (concepto, no implementado)
    CAPSULE   -> que contexto recibe el agente

Despues del experimento DSH, queda clara una cuarta:
    EVIDENCE  -> que observo realmente una ejecucion

La evidencia producida por una ejecucion merece identidad propia.
No es lo mismo que un log. Es: TASK_ID, commit base, hash de
entradas, operaciones ejecutadas, operaciones NO ejecutadas,
incertidumbres, contradicciones encontradas.

### Vocabulario de incertidumbre formalizado

Estados que NO son equivalentes:
    UNKNOWN              -> no sabemos
    UNABLE_TO_ESTIMATE   -> sabemos que no podemos estimar
    NOT_OBSERVED         -> no se observo, podria observarse
    NOT_APPLICABLE       -> no aplica a este caso

Conviene declararlos explicitamente cuando se produce evidencia.

### Cambio de paradigma

Pregunta anterior: como hacemos para que la IA tenga suficiente
contexto?

Pregunta nueva: como hacemos para que la IA pueda verificar el
mundo real cuando el contexto esta incompleto?

Principio derivado:
    CONTEXTO  = orientacion
    EVIDENCIA = verificacion

El contexto puede quedar desactualizado. El disco, el runtime, los
servicios y los datasets son la realidad operacional.

### Matiz metodologico: autocorreccion acotada

DSH detecto un error en su propio parser durante la mision. Eso

autocorreccion robusta en general. La distincion es importante

### Human Gate — acciones que siempre requieren autorizacion

cambio de permisos, exposicion de puertos, cambios de firewall
